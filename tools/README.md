# tools — добавление товаров WERA на tl-shop.com.ua (Horoshop, store `tlshop`)

Скрипты Node.js для задачи «Есть у GRN, нет у нас» (`inventory/add_422_plan.xlsx`): анализ, сборка партий новых товаров, запись через Horoshop MCP с проверками.

Код лежит в git. Данные остаются локально, их исключает `tools/.gitignore`: json с ценами и выгрузками, даташиты, фото-кэш, `node_modules`.

## Установка

```
cd tools
npm install          # exceljs, sharp, pdfjs-dist, puppeteer-core, xlsx
```

MCP-сервер Horoshop берётся из `~/.claude.json` (`mcpServers.horoshop`), так же как в Claude Code. Паролей в скриптах нет, `stores.json` они не читают.

## Структура

| Путь | Что делает |
|---|---|
| `mcp.js` | Один вызов инструмента MCP: `node mcp.js <tool> <args.json> <out.json>`. Медленно: при каждом запуске заново входит в админку (~75 с). |
| `lib/session.js` | Одна MCP-сессия на много вызовов (~5 с на вызов). Используют `run_batch.js`, `form.js`, `guarantee.js`. |
| `lib/vt.js` | Таблицы вариантов в описаниях: разбор блока таблицы, строк (артикул берётся из текста ячейки, не из ссылки), заголовков, перерисовка строки «цей товар» и ссылок. Адрес из названия (`×` → `x`, `1,0×5,5` → `1-0x5-5`). Квадратное фото 1000×1000. |
| `vt/table2.js` | Разметка таблицы и блока «паспорт PDF» в стиле сайта. |
| `vt/fetchpage.js` | Загрузка страницы витрины с прохождением cookie-проверки. |
| `lib/build.js` | Сборка партии (модуль): описание по даташиту и строке таблицы серии у соседа, payload создания, payload ссылок у соседей. Проверка: таблица у соседа может поменяться только ссылками. |
| `lib/run_batch.js` | **Полный цикл одной партии** с жёсткими стопами (см. ниже). |
| `lib/batch.js` | Ручные шаги партии: `photos`, `payload`, `links`. |
| `lib/form.js` | Ручной шаг формы: адрес, SEO title/description UA/RU, гарантия «Виробник, 12 міс.». `dry` / `real`; при `real` пишет только то, что прошло dryRun без лишних полей. Выгрузка до и после, сверка. |
| `lib/guarantee.js` | Разово: гарантия товарам пилота и партии 1. |
| `lib/dstext.mjs` | Текст даташита WERA по строкам: `node lib/dstext.mjs file.pdf`. |
| `pdfjpg.js` | Извлечь JPEG из PDF даташита: `node pdfjpg.js file.pdf prefix`. |
| `a422/list.js` | 422 строки листа «Есть у GRN, нет у нас» → `list.json`. |
| `a422/wscan.js` | wera.de/de/<артикул> по каждому артикулу (раз в 1,5 с) → `wscan.json`: страница, id серии, имя главного фото. |
| `a422/tables.js` | Из полной выгрузки каталога (`d*_out.json`) → `tables.json` (в каких наших таблицах артикул стоит без ссылки) и `ours.json`. |
| `a422/classify.js` | Группы А/Б/В/Знятий, соседи, предложенный раздел → `classified.json`. |
| `a422/price.js` | Цена: сайт GRN; РРЦ из `inventory/wera_price.xlsx` (лист «WERA 2026 GRN»), если GRN ниже больше чем на округление → `price.json`. |
| `a422/build.js` | `inventory/add_422_plan.xlsx`. |
| `a422/group_v.js` | `inventory/group_v_proposal.xlsx`: предложенные разделы для группы В. |
| `a422/progress.js` | `inventory/add_422_progress.json`, `created_today.xlsx`, `deferred.xlsx`. Созданные товары берёт из `batches/*/links.json`, отложенные — из `a422/deferred.json` и товаров без цены. |
| `batch/sheets.js`, `batch/dupes.js` | Листы фото из даташитов; поиск одного фото на несколько размеров (общий снимок серии). |
| `batches/<name>/` | Одна партия: `batch.json`, `content.js` (названия и тексты UA/RU по даташиту), `photosrc.json`. После запуска там же `payload_new.json`, `ids.json`, `links.json`, `report.json`. |
| `grn/` | Обход сайта GRN (`crawl.js`, по robots.txt, раз в 10 с), сравнение (`compare2.js`), сверка цен (`price65.js`). GRN — только источник фактов (артикул, цена, наличие). |

## Партия: порядок

1. Создать `batches/<name>/batch.json` (артикулы) и `content.js`: названия в нашем формате и тексты по даташиту WERA, без выдумок. Пример — `batches/b4/content.js`.
2. `photosrc.json`: своё фото из даташита (`batch/ds/<art>_3_*.jpg`). Если его нет — общее фото серии с wera.de (`wimg/<имя>.webp`). Нельзя фото, на котором читается **другой** размер.
3. `node lib/run_batch.js batches/<name>`:
   1. бэкап соседей → `backup/<name>_neighbours_before.json`;
   2. предпроверка: строки таблицы нового товара = строки серии у соседа; таблица каждого соседа меняется **только ссылками**. Иначе товар → `a422/deferred.json`, не пишется;
   3. фото → `images/<name>/`, commit + push, проверка raw-ссылок GitHub;
   4. импорт: dryRun должен показать только новые товары и только запланированные поля, иначе **стоп партии**; затем запись;
   5. форма (адрес, SEO, гарантия): dryRun каждого товара. Поле вне плана → товар в отложенные, форма не пишется. Выгрузка до/после: изменилось что-то кроме адреса → восстановление импортом + отложено (правило CLAUDE.md про `alt_parent`);
   6. ссылки в таблицах: dryRun может менять только описания запланированных товаров, иначе **стоп**; запись; сверка соседей с бэкапом (кроме ссылок ничего);
   7. витрина: 2 товара UA/RU (title, таблица, PDF);
   8. `a422/progress.js`, запись в `backup/variants_log.jsonl`.
4. Код возврата: `0` — готово, `2` — стоп по партии (причина в `report.json`), `1` — ошибка.

## Правила (кратко)

- Цена — с сайта GRN; если GRN ниже РРЦ больше чем на округление — РРЦ (half-up).
- Название: `Біта TORX® 867/4 Z TX 20×70 мм WERA 05060110001`; размеры «2,0», «×», пробел после PH/PZ/TX/HEX.
- Наличие, внутренние коды (TL…), адреса существующих товаров не трогать. Ничего не удалять.
- Никаких текстов, фото и упоминаний GRN на сайте.
